    04 · 业务流程¶

    本章用 mermaid 描述核心端到端流程。
    业务状态机、订单流转、资金流向在这里统一约定。

    4.1 业务全景¶

    flowchart LR
  subgraph 患者侧
    P1[注册/登录] --> P2[实名认证]
    P2 --> P3[浏览医院/服务包]
    P3 --> P4[创建订单]
    P4 --> P5[支付]
    P5 --> P6[等待匹配]
    P6 --> P7[服务中]
    P7 --> P8[完成+评价]
  end

  subgraph 陪诊师侧
    E1[注册] --> E2[提交资质]
    E2 --> E3[培训考核]
    E3 --> E4[审核通过]
    E4 --> E5[抢单/接单]
    E5 --> E6[到院服务]
    E6 --> E7[结束服务]
    E7 --> E8[结算+提现]
  end

  subgraph 平台侧
    A1[订单分配]
    A2[资金清算]
    A3[客服介入]
  end

  P6 -.匹配.-> A1
  A1 -.派单.-> E5
  P7 -.投诉.-> A3
  E7 -.结算.-> A2
  A2 -.打款.-> E8

    4.2 陪诊师入驻流程（详细）¶

    flowchart TD
  A[下载/打开App] --> B[选择'我是陪诊师']
  B --> C[手机号+验证码注册]
  C --> D[完善个人信息]
  D --> E[实名认证]
  E --> F{通过?}
  F -- 否 --> E
  F -- 是 --> G[上传健康证+资质]
  G --> H[选择服务范围]
  H --> I[学习培训课程]
  I --> J{全部完成?}
  J -- 否 --> I
  J -- 是 --> K[参加培训考核]
  K --> L{≥80分?}
  L -- 否 --> K
  L -- 是 --> M[签署协议]
  M --> N[提交审核]
  N --> O{运营审核}
  O -- 拒绝 --> P[通知拒绝原因+重新提交]
  O -- 通过 --> Q[正式上线,可接单]
  P --> G

    4.3 患者下单 → 服务完成（端到端主流程）¶

    flowchart TD
  start([患者进入下单]) --> A[选择医院]
  A --> B[选择服务包]
  B --> C[选择时间+就诊信息]
  C --> D[选择陪诊师]
  D --> D1{匹配模式}
  D1 -- 系统匹配 --> D2[根据地理/时间/技能计算候选]
  D1 -- 指定陪诊师 --> D3[校验陪诊师可服务性]
  D2 --> E[生成订单]
  D3 --> E
  E --> F[支付]
  F --> F1{支付成功?}
  F1 -- 否 --> F2[订单关闭+提示]
  F1 -- 是 --> G[订单进入匹配池]
  G --> H{匹配方式}
  H -- 抢单 --> H1[推送至抢单池]
  H -- 派单 --> H2[定向派给某陪诊师]
  H1 --> I{陪诊师接单}
  I -- 30s 超时 --> H1
  I -- 接单成功 --> J[订单进入服务中]
  I -- 无陪诊师接 --> K[30分钟未匹配升级人工]
  H2 --> J
  J --> L[陪诊师到院签到]
  L --> M[关键节点打卡]
  M --> M1{异常?}
  M1 -- 是 --> M2[上报异常+客服介入]
  M1 -- 否 --> N[服务结束提交]
  N --> O[患者确认结束]
  O --> P{有补差价?}
  P -- 是 --> Q[补差价支付]
  P -- 否 --> R[订单完成]
  Q --> R
  R --> S[双方评价]
  S --> T[订单结算]
  T --> U([完成])
  K --> V[人工客服介入匹配或退款]

    4.4 订单状态机¶

    2026-09-24 状态机统一：新增 pending_await、settling、disputed 三个状态。 详情见 docs/superpowers/plans/2026-09-24-state-machine.md。

    stateDiagram-v2
  [*] --> Created: 患者创建
  Created --> Paid: 支付成功
  Created --> Closed: 超时未支付
  Paid --> Matching: 进入匹配池
  Matching --> PendingAcceptance: 陪诊师抢单(锁单30s)
  Matching --> Accepted: 派单直签
  Matching --> Refunding: 30min未匹配/患者主动取消
  PendingAcceptance --> Accepted: 陪诊师30s内确认
  PendingAcceptance --> Matching: 30s未确认/陪诊师拒接
  PendingAcceptance --> Refunding: 取消
  Accepted --> InService: 陪诊师到院签到
  InService --> Completed: 服务结束+患者确认
  InService --> Disputed: 投诉/异常
  Accepted --> Disputed: 投诉/异常
  Completed --> Reviewed: 双方评价
  Completed --> Refunding: 申请退款(争议中)
  Completed --> Settling: 直接进入结算
  Completed --> Disputed: 投诉
  Reviewed --> Closed: 结算完成
  Disputed --> Completed: 客服判定正常完成
  Disputed --> Refunding: 客服判定退款
  Disputed --> Closed: 客服判定无效
  Refunding --> Refunded: 退款成功
  Refunding --> Settling: 退款完成入结算
  Refunded --> Settling: 进入结算
  Settling --> Closed: 结算完成
  Closed --> [*]
  Canceled --> [*]

    任何状态变更都需写入 order_event 表，作为时间线和审计依据。 锁单超时由 services/order/internal/scheduler.ExpiredLockScanner（5s 扫一次）配合完成（§4.2 order-lock plan 实施）。

    抢单锁单三道防线（§4.2 order-lock plan）¶

    陪诊师接单流程：

    1. Redis SETNX orders:accept-lock:{order_id} 30s（Redis 不可用时降级跳过，DB 兜底）
    2. DB 校验 status='matching' AND version=N
    3. DB UPDATE status='pending_acceptance', lock_owner=escort_id, lock_expire_at=NOW()+30s
    4. 通知陪诊师 "30s 内确认"
    5. 陪诊师 30s 内 confirm → status='accepted'；超时则 ExpiredLockScanner 每 5s 扫一次，自动 ReleaseAcceptLock 回退 matching 并发 OrderMatchingEvent

    4.5 智能匹配规则（v1 简版）¶

    flowchart LR
  O[新订单] --> F1{已指定陪诊师?}
  F1 -- 是 --> F2[校验时间+技能+距离]
  F1 -- 否 --> F3[按规则计算候选]

  F3 --> S1[城市匹配]
  S1 --> S2[服务时段匹配]
  S2 --> S3[擅长医院/科室加分]
  S3 --> S4[评分≥4.5加分]
  S4 --> S5[距离≤3km加分]
  S5 --> S6[历史爽约率≤5%]
  S6 --> R[Top N 候选]
  R --> P[推送抢单池 / 或派单]

  F2 --> G{可服务?}
  G -- 否 --> N[提示用户更换]
  G -- 是 --> H[生成订单]

    v1.0 使用规则匹配；v2.0 引入 ML 模型做最优匹配。

    4.6 支付与结算¶

    sequenceDiagram
  participant U as 患者
  participant P as 平台
  participant W as 微信支付
  participant E as 陪诊师
  participant B as 银行/微信钱包

  U->>P: 创建订单(¥300)
  P->>W: 下单(¥300)
  W-->>U: 唤起支付
  U->>W: 输入密码
  W-->>P: 支付成功回调
  P-->>U: 订单进入匹配

  Note over P,E: 服务完成后
  E->>P: 申请结算
  P->>P: T+7冻结期
  P->>B: 打款(¥300-佣金)
  B-->>E: 到账
  P->>W: 退款(若有)

    资金要点：

    • 平台账户与用户资金严格隔离，禁止挪用用户预付款（合规要求）
    • 抽佣比例可配置（默认 20%）
    • 退款阶梯（refund plan：4 档默认策略，refund_policies 表可热加载）：
    触发时机 退款比例 陪诊师补偿 退款路径
    付款前取消 100% 0% 原路退（无）
    付款后 5 分钟内 100% 0% 微信支付原路退
    5 分钟~接单前 100% 0% 同上
    接单后~服务开始前 95% 5%（陪诊师补偿） 同上
    服务已开始 0% 0% 走 dispute / 工单

    v1 不接第三方支付真实退款 API；refund.Service.Refund 在 approved 时直接落 refunds.status='completed' + external_tx_id='mock-tx-N'。v2 接微信支付 V3 退款接口。

    flowchart LR

  C -- 否 --> D[14天评价期]

    4.9 紧急安全（SOS）¶

    sequenceDiagram
  participant U as 患者/陪诊师
  participant APP as 端App
  participant P as 平台
  participant C as 紧急联系人
  participant S as 公安/急救

  U->>APP: 长按SOS 3s
  APP->>P: 触发SOS事件(订单/位置/时间)
  P->>P: 创建紧急工单
  P->>C: 发送短信+推送(定位链接)
  P->>S: 视情况联动(可选,需用户预授权)
  APP->>U: 持续录音/录像(可选)
  Note over APP,P: 后台每30s上报位置

    4.10 提现流程（陪诊师）¶

    flowchart LR
  A[发起提现] --> B{可提现余额≥100?}
  B -- 否 --> N1[提示最低金额]
  B -- 是 --> C[校验实名+绑定卡]
  C --> D[风控校验]
  D --> E{通过?}
  E -- 否 --> N2[提示风险拒绝]
  E -- 是 --> F[创建提现工单]
  F --> G[财务审核(自动/人工)]
  G --> H[调用微信/银行打款]
  H --> I[到账通知]

    4.11 异常分支汇总¶

    场景 触发 处理
    支付失败 网络 / 余额不足 重试或换支付方式
    30 分钟未匹配 抢单池无响应 自动扩大匹配范围；30min 后人工介入
    陪诊师迟到 > 15min GPS 时间比对 自动通知患者 + 客服介入改派
    陪诊师拒绝服务 接单后取消 扣信用分；订单回到匹配池
    患者爽约 陪诊师到院签到后 30min 患者未出现 通知患者 → 自动结单 → 部分退款
    服务中突发 双方任一上报 客服介入
    投诉差评 评价 ≤ 3 星 客服介入 → 申诉通道
    退款争议 任一方发起 工单处理；必要时法务介入
