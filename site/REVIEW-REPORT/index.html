    评审报告 · 陪诊师平台需求文档 v1.0¶

    评审对象：F:\ai\doctors\docs\ 目录下 10 个 Markdown 文档（v1.0 初稿）
    评审视角：冷启动式独立评审 / 模拟评审会
    评审方法：逐章阅读 + 跨章一致性比对 + 业务逻辑反证 + 合规与可测试性穿透
    评审时间：2026-09-23

    整体评级¶

    • 总体评级：B（良好，需补救）

    文档整体框架完整、阅读路径清晰、术语基本对齐；流程图（mermaid）使用熟练、合规边界声明到位、账号体系与权限矩阵结构合理。 但 v1.0 距离可投产还有 3 类硬伤： 1. 跨文档不一致较为突出（状态机在 04 vs 07、API 路径在 06 vs 08、P0/P1 范围在 03 vs 09），可能直接误导研发； 2. 核心业务规则颗粒度不足（抢单并发、退款分段、虚拟号对接、T+7 结算期退款处理），易在上线后产生客诉与资损； 3. 合规与运营支撑类章节缺位（埋点、客服 SLA、灰度/回滚 SOP、AB 实验、数据迁移、灾备演练、保险接入），风险预案不闭环。

    建议：修复全部 Critical + 50% 以上 Important 后再启动开发。Critical 项属于"不修不能写代码"的级别。

    各维度评分¶

    维度 评分 简评
    内容完整性 C 9 章覆盖尚可，但缺少埋点、客服 SLA、灰度/回滚 SOP、AB 实验、缓存策略、数据迁移、灾备演练、保险接入等关键章节
    跨文档一致性 C 状态机 / API 路径 / 优先级在 03-04-06-07-08-09 间出现多处不一致
    业务逻辑合理性 B- 主流程合理，规则匹配、退款分段、抢单并发等需补充细节
    合规与风险边界 B "陪诊 ≠ 诊疗"声明充分；但 SOS 录音、PII 最小必要、出险责任、商户号资质落地不足
    可测试性 / 可验收性 C+ 验收 Checklist 颗粒度过粗，缺测试方法与渗透/等保标准对齐
    技术可行性 B- 技术选型主流，但 unionid/openid、分库分表前后矛盾需澄清
    文档工程 B+ 编号、跳转、表格总体规范；图表使用良好；术语表略薄

    Critical 问题（必须修复，否则不能上线）¶

    C-01：订单状态机在 04 与 07 之间定义不一致¶

    • 位置：04-业务流程.md 4.4 节（line 120-140）vs 07-数据模型.md 7.3.1 节（line 297-315）
    • 问题描述：
    • 04 状态机共 11 个状态：Created / Paid / Matching / Accepted / InService / Completed / Reviewed / Settling / Refunding / Refunded / Closed（settling 仅在 07 中出现，04 状态图里是 Reviewed → Settled，跳过了 Settling）
    • 07.3.1 表中状态有 12 个：settling 作为独立态被列出
    • 04 中缺少 Pending_Acceptance（抢单 30s 锁单期间的中间态），与 03.3.3 的"30s 锁单"无法对应
    • 影响：开发拿 04 写代码、测试拿 07 对账，状态映射缺失会引发"脏数据状态"无定义可循；客服判定时也会出现"订单到底在哪个状态"的扯皮
    • 修复建议：选定一份作为主源（建议 04，流程图可读性强），07 状态表按 04 重排；增补 Pending_Acceptance（抢单锁单态）、Settling（结算中）、Disputed（争议中）三个中间态；二者必须一一对应

    C-02：P0 功能范围在 03 与 09 之间严重不一致¶

    • 位置：03-功能需求.md 3.6 节（line 385-393）vs 09-验收与发布.md 9.2 节（line 17-52）
    • 问题描述：
    • 03.6 P0 明确包含："注册、实名、医院浏览、下单、匹配、接单、服务、支付、评价"
    • 03.6 P1 包含："优惠券、抢单池、虚拟号、客服工单、数据看板"
    • 09.2.1 P0 验收清单却要求："申请退款、SOS 一键报警触发紧急联系人推送、个人中心、优惠券、地址管理" → 其中退款、SOS、优惠券在 03.6 中不是 P0
    • 09.2.2 P0 要求："钱包可见收入 / T+7 冻结 / 提现申请" → 03.6 未明确提现归属
    • 09.2.3 P0 要求："工单 + 客服首响 SLA 监控" → 03.6 把"客服工单"放在 P1
    • 影响：测试会按 09.2 全量验，开发按 03.6 P0 砍功能 → 上线时验收不过
    • 修复建议：建立一张权威优先级表作为附录，所有文档引用同一份。建议同步把退款、SOS、虚拟号、工单升入 P0（这才是 MVP 真实需要），并改写 03.6

    C-03：API 路径在 06 与 08 之间不对得上¶

    • 位置：06-系统架构.md 6.3 节（line 123-138）vs 08-接口需求.md 8.3-8.5 节（line 41-145）
    • 问题描述：
    • 06.3 给出"关键接口"清单：GET /match/candidates、POST /withdrawals、POST /messages/dispatch、POST /sos/trigger、POST /reviews
    • 08 中完全没有上述接口，对应实现分散在不同前缀，如 POST /api/v1/wallet/withdrawals（08.4.3）
    • 06.3 没有统一前缀 /api/v1，08.1 规定必须统一前缀（line 12），规则相互冲突
    • 06.2 架构图中把 IM（即时通讯）作为独立服务，但 08 没有 IM 接口说明
    • 影响：前端按 08 写请求、后端按 06 起路由 → 404 漫天飞；OpenAPI 文档与架构图无法对齐
    • 修复建议：06.3 改为"接口列表详见 08"，自身只保留服务拆分与职责；要求 08 覆盖所有对外接口（含匹配、SOS、消息、IM）；统一前缀强制为 /api/v1，06.3 表格中标明

    C-04：抢单并发与一致性方案未给出，"先到先得 30s 锁单"无落地¶

    • 位置：03-功能需求.md 3.3.3 节（line 246-256）、04-业务流程.md 4.3 节（line 92-99）、04-业务流程.md 4.4 节（line 118-140）
    • 问题描述：
    • 03.3.3 说"抢单（先到先得，30s 锁单）"，04.3 说"陪诊师接单 30s 超时"
    • 04.4 状态机里没有任何"锁单中 / 待接单确认"中间态
    • 07 数据模型里 order.status 也没有 lock_token / locked_by / lock_expire_at 字段
    • 完全没回答：高并发下 N 个陪诊师同时抢同一单如何保证唯一赢家？是用 Redis SETNX？DB 唯一索引 + 版本号？分布式锁？消息队列串行化？
    • 05.1.3 说"按 user_id 哈希分库分表"，跨库抢单的分布式事务如何处理？
    • 影响：抢单超卖 / 一单多接是平台级事故，会直接触发客诉和资损
    • 修复建议：
    • 在 04.4 增加 Pending_Acceptance 状态、order.lock_owner / lock_expire_at 字段（07.2.3 增补）
    • 06 / 04 中明确给出抢单落地方案（推荐 Redis SETNX + DB 唯一约束双重防护）
    • 09 验收清单加入"并发抢单压测用例：100 并发抢同一单，赢家唯一"

    C-05：退款规则分段过于粗糙，缺服务节点映射，缺 T+7 结算期内退款的资金路径¶

    • 位置：04-业务流程.md 4.6 节（line 197-205）、03-功能需求.md 3.3.5 节（line 271-276）
