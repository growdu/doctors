## §1 项目概览与技术栈

### 1.1 这是什么

陪诊师平台（Doctors）连接 **患者** 与 **陪诊师**：患者下单 → 平台撮合 → 患者选人 → 陪诊师 30s 确认 → 上门服务 → 评价 → 完成。配套有实名 / 钱包 / 退款 / SOS / 评价 / 站内信 / 后台审核等横切能力。

代码是 mono-repo：前端 1 个 uni-app 工程 + 后端 11 个 Go 服务 + 1 个 shared 公共包。

### 1.4 怎么选择在哪里改代码

```
要做什么？
   │
   ├── 改/加前端页面 ───────→ frontend/unified-app/src/pages/
   │                            ├── patient/  患者域（受 RoleGuard 限制 only patient）
   │                            ├── escort/   陪诊师域
   │                            ├── admin/    运营后台
   │                            └── home/     域切换首页 + 域名选择
   │
   ├── 改/加前端通用组件 ───→ frontend/unified-app/src/components/shared/
   │
   ├── 改/加前端 API 客户端 → frontend/unified-app/src/api/<service>.ts
   │
   ├── 改/加后端 Go 接口 ──→ services/<service>/internal/handler/
   │                            handler 薄薄一层：参数解析 + 调 service + 返回
   │
   ├── 改业务逻辑 ─────────→ services/<service>/internal/service/
   │                            service 编排 handler 与 repo,事务边界在此
   │
   ├── 改数据库 schema ────→ migrations/000N_xxx.up.sql (+ .down.sql)
   │                            然后 services/<service>/internal/repo/xxx.go 改 SQL
   │
   ├── 改共享类型 ─────────→ shared/contracts/    （Go interface / struct / 事件常量）
   │   多个服务都要用
   │
   └── 加新共享能力 ───────→ shared/ 新建子包;若 gin 中间件则放 shared/middleware
```

> ⚠️ **不要做的事**：
> - 不要在 `services/<svc>/internal/` 之外写业务逻辑。
> - 不要绕过 `shared/contracts` 自己定义 DTO；任何出现在两个以上服务的 struct 必须先在 contracts 定义。
> - 不要在 frontend 直接写 `fetch / axios` —— 全部走 `src/api/client.ts` 统一封装的 `request()`。

时序要点：
1. **状态机驱动**所有状态转换,转换合法性在 `services/order/internal/state/` 校验（详见 §5.1）。
2. **Redis lock 防重入**:`selecting → pending_acceptance` 的 30s 窗口用 `orders:confirm:{order_id}` 锁保护。
3. **Kafka publish-after-commit**:事件必须落库后再发布,避免幽灵事件。
4. **WS push** 给陪诊师 App 的"收到新邀请"实时通知也是这条路径产生的副作用。

### 2.5 关键架构决策（ADR 简要）

| # | 决策 | 取舍 |
|---|---|---|
| ADR-001 | unified-app 单工程多域（v2 合并 admin+patient+escort）| 优点：1 套构建、1 套组件库、1 套状态管理；缺点：uni-app 包大小稍大 |
| ADR-002 | 跨服务不直连,走 Kafka 事件 | 优点：解耦 + 异步 + 可重放；缺点：最终一致；订单创建 → 钱包 T+7 必须事件驱动 |
| ADR-003 | 状态机放在 order-service 而非 DB ENUM | 优点：复杂转换可编程校验；缺点：DB 不强制状态合法性,依赖应用层 |
| ADR-004 | T+7 结算钱包（未 T+0）| 控制退款窗口风险,见 §5.2 |
| ADR-005 | 退款 3 段式（部门审批 → 财务审批 → 出纳打款）| 财务合规要求,见 §5.3 |
| ADR-006 | Pinia setup-syntax 写 store | TS 推导完整,无需 `$patch` hack |
| ADR-007 | API 客户端用 `request()` 统一封装（无 axios） | 减小 mp-weixin 端包体积;`client.ts:24` |
| ADR-008 | 共享类型放 Go 而非 TS 自动生成 | 当前只在后端契约化,前端手维护 DTO（标记 §48.M 已对齐 snake_case）|

### ADR-009 v2.1 消息同步模式（短轮询 vs 推送）

- **状态**:Accepted
- **日期**:2026-10-15
- **背景**:v2.1 上线后前端需获知后端消息状态（read / favorite）。需要在"轮询"和"推送"间选择。
- **决策**:**采用 30s 短轮询 + `visibilitychange` 暂停**。文件 `frontend/unified-app/src/utils/sync.ts`。
- **后果**:
  - ✅ 实现简单,1 个 setInterval + 1 个 visibilitychange listener
  - ✅ 后端零改动,只暴露 GET 端点
  - ✅ 零依赖 key 路径（visibilitychange + 离线缓存）
  - ❌ 高负载下不可用（>10k 在线需 N 台 message-service）
  - ❌ 30s 延迟影响"实时"体感
- **替代方案**:
  - WebSocket:Kafka 后端 + socket.io 前端,改造面大
  - SSE（EventSource）:单向、HTTP 友好,但需后端长连接管理
- **回退条件**:日活在 v2.2 评估;若 P95 延迟 > 5s 或消息量 > 1k QPS,启动 v2.2 评估 SSE。

### 3.3 路由机制（pages.json）

uni-app 的路由**不是** vue-router,而是 **类小程序 pages.json** 的静态声明。每个 `.vue` 页面必须在 `pages.json` 的 `pages[]` 里登记才能被访问。

```jsonc
// pages.json 片段
{
  "pages": [
    { "path": "pages/home/index",                  "style": { "navigationBarTitleText": "陪诊师" } },
    { "path": "pages/patient/index/index",          "style": { "navigationBarTitleText": "首页" } },
    { "path": "pages/patient/order/list",          "style": { "navigationBarTitleText": "我的订单" } },
    { "path": "pages/admin/dashboard/index",       "style": { "navigationBarTitleText": "Admin" } },
    { "path": "pages/escort/profile/index",        "style": { "navigationBarTitleText": "我的" } }
    // ...
  ],
  "tabBar": {
    "color": "#999", "selectedColor": "#07c160",
    "list": [
      { "pagePath": "pages/patient/index/index", "text": "首页" },
      { "pagePath": "pages/patient/order/list",  "text": "订单" },
      { "pagePath": "pages/patient/profile/index","text": "我的" }
    ]
  }
}
```

> ⚠️ **路径陷阱**:`pages/patient/order/list.vue` 的 path 是 `pages/patient/order/list`（**不带 .vue**）。`uni.navigateTo({ url: '/pages/patient/order/list' })`。

跳转 API（**不是** vue-router 的 `router.push`,直接挂 `uni` 全局）：

```ts
// ✓ 路由跳转（保留当前页）
uni.navigateTo({ url: '/pages/escort/wallet/index' });

// ✓ 重启到首页栈（清栈）
uni.reLaunch({ url: '/pages/home/index' });

// ✓ 切换 tabBar 项
uni.switchTab({ url: '/pages/patient/index/index' });

// ✓ 后退 N 步（默认 1）
uni.navigateBack({ delta: 2 });
```

> 所有 `navigateTo` 都用 **绝对路径** `/pages/...`。`uni.reLaunch` 常用于"从 modal 确认后重置到首页"或"角色切换后回 home shell"。

### 3.4 状态管理（Pinia setup-syntax）

#### 3.4.1 auth store（核心示例）

```
src/store/auth.ts
┌────────────────────────────────────────────────────────────────┐
│ defineStore('auth', () => {                                    │
│   // ── state ──                                              │
│   const token = ref('')                                        │
│   const user  = ref<MeResponse | null>(null)                  │
│                                                                │
│   // ── getters ──                                            │
│   const isAuthed   = computed(() => !!token.value && !!user)  │
│   const activeRole = computed(() => user.value?.active_role)   │
│   const roles      = computed(() => user.value?.roles ?? [])   │
│                                                                │
│   // ── actions ──                                            │
│   function bootstrap()       { token/user ← localStorage }    │
│   async function login()     { token = await loginByPhone() }  │
│   async function switchRole(){ token = await switchActive() } │
│   async function refreshMe() { user = await fetchMe() }       │
│   function onUnauthorized()  { token=''; user=null; reLaunch }│
│                                                                │
│   return { token, user, isAuthed, activeRole, roles, ... }     │
│ })                                                             │
└────────────────────────────────────────────────────────────────┘
```

#### 3.4.2 多角色 + 路由守卫

陪诊师账号可以同时有 `patient` 角色,管理员可以兼 `cs`、`order_admin` 等。**登录态独立,激活态切换**。

```
用户场景：某账号 roles = ['patient', 'escort']
   │
   ├─ ① active_role = 'patient' → 进入 patient 域
   │     RouteGuard 检查：user.roles.includes('patient') ✓
   │
   └─ ② 用户点击 RoleSwitcherModal → switchRole('escort')
         │
         ├─→ auth.switchRole('escort')
         │      ├─→ POST /auth/switch-role { role }
         │      └─→ 拿到新 token,active_role = 'escort'
         │
         └─→ uni.reLaunch('/pages/escort/orders/index')
              └─→ 新页面读 auth.activeRole = 'escort'
                  └─→ 列表数据按 escort 视角拉（role=escort）
```

#### 3.4.3 在组件里读 store

```vue
<script setup lang="ts">
import { useAuthStore } from '@/store/auth';
const auth = useAuthStore();

// 读 ref:auth.user、auth.activeRole、auth.isAuthed（Pinia 自动 unwrap）
</script>
```

> ⚠️ **不要直接用 `$store.auth.user` 这种 options-store 写法**。store 是 setup-store,只能通过 `useAuthStore()` 拿到代理。

### 3.5 API 层（client + 各 service 模块）

```
src/api/
├── client.ts                          ← request() 封装
│     │
│     │  类型:
│     │    RequestOptions { url; method?; data?; baseURL?; headers? }
│     │    ApiError      { code; message; status?; raw? }
│     │
│     │  行为:
│     │    request() 做 4 件事:
│     │    1. 组装 URL (baseURL + url)
│     │    2. 注入 Authorization: Bearer <token> （从 auth store 读）
│     │    3. fetch + .json()
│     │    4. 后端 code != 0 抛 ApiError（含 code / message / status）
│     │       - 401 → auth.onUnauthorized()
│     │       - 429 → Toast + throw
│     │       - 5xx → '网络繁忙' + throw
│     │
│     │  测试:
│     │    client.spec.ts: mock fetch,断言 Authorization header / 错误归一化
│     │
└── order.ts (示例)
      │
      │  类型:
      │    export interface Order { id, status, amount, ... }
      │    export interface CreateOrderRequest { ... }
      │
      │  endpoint:
      │    export async function listOrders(q: ListOrdersQuery = {}): Promise<{ items, total }> {
      │      return request({ url: `/api/v1/orders?${qs}`, baseURL: ORDER_BASE_URL })
      │    }
      │
      │  测试:
      │    order.spec.ts: vi.mock('@/api/client', ...) → assert 调 client.request 时用对的 url/method/baseURL
```

**API 层的设计原则**（详细 §6）：

1. **零业务规则**：API 层只翻译 URL / header,不放校验 / 状态机。
2. **类型先行**：每个 endpoint 的入参 / 出参写 interface,被 spec 文件 import 验证。
3. **snake_case 字段**：与后端 contracts 对齐,前端不做大小写转换（v2 §48.M 统一）。

## §3.9 国际化(i18n)

### 3.9.1 机制

- 库:`vue-i18n@9`(已在 `package.json`)
- 默认 fallback:`zh-CN`
- 命名约定:`<domain>.<entity>.<field>`,例:`escort.profile.balance`、`patient.order.checkin.title`

### 3.9.2 三端差异

| 端 | locale 来源 | 切换方式 |
|---|---|---|
| h5 | `navigator.language` + localStorage `h5.locale` | `i18n.global.locale.value = ...` |
| mp-weixin | `uni.getStorageSync('locale')` | `uni.setStorageSync` + reload |
| app-plus | 同 mp-weixin + 系统语言 fallback | 同上 |

### 3.9.3 缺失 key 监控

```ts
// src/i18n/index.ts
import { createI18n } from 'vue-i18n'
import * as Sentry from '@sentry/vue'
// import messages from './messages'

export const i18n = createI18n({
  legacy: false,
  locale: uni.getStorageSync('locale') ?? 'zh-CN',
  fallbackLocale: 'zh-CN',
  messages,
})

i18n.global.setMissingHandler((key: string) => {
  Sentry.captureMessage(`i18n missing: ${key}`, 'warning')
  return `[${key}]`  // dev 环境渲染, prod 静默
})
```

### 4.2 handler / service / repo 三层各自的职责

| 层 | 职责 | 不该做的事 |
|---|---|---|
| **handler** | • 解析 HTTP 入参（JSON / query / path）<br>• 调 service<br>• 转 DTO + 返回 JSON | • 不写业务规则<br>• 不调用 repo（除了特殊情况,如 GET 列表绕过 service）<br>• 不读环境变量 |
| **service** | • 业务校验（参数合法性 / 状态机 / 库存 / 限额）<br>• 编排 repo（多步写 / 跨 DB）<br>• 调 Kafka publisher（commit-after-publish）<br>• 调 lock / cache | • 不直接拼 SQL<br>• 不直接读 config.Get()<br>• 不做 HTTP 解析 |
| **repo** | • 拼 SQL + 跑 pgx<br>• 错误归一化为 `errs.ErrNotFound` / `errs.ErrConflict`<br>• 幂等（同 ID 多次写同一 status 不应重复插入事件） | • 不做业务校验<br>• 不调 service / handler<br>• 不发 Kafka |

> 单元测试时，**测 service 时 mock repo 接口；测 repo 时用 testcontainers 起真实 PG**。纯单元测试不依赖外部。

```
举例：

package state

type OrderStatus string

const (
    StatusSelectingEscort       OrderStatus = "selecting_escort"
    StatusEscortPendingAccept   OrderStatus = "escort_pending_acceptance"
    StatusEscortConfirmed       OrderStatus = "escort_confirmed"
    StatusInService             OrderStatus = "in_service"
    StatusCompleted             OrderStatus = "completed"
    StatusCancelled             OrderStatus = "cancelled"
    // ... + pending_escort 是 v1 旧状态,残留兼容
)

// 合法转换表(单向,注意取消可从多个状态发起)
var validTransitions = map[OrderStatus][]OrderStatus{
    StatusSelectingEscort:     {StatusEscortPendingAccept, StatusCancelled},
    StatusEscortPendingAccept: {StatusEscortConfirmed, StatusCancelled, StatusSelectingEscort}, // 超时回退
    StatusEscortConfirmed:     {StatusInService, StatusCancelled},
    StatusInService:           {StatusCompleted, StatusCancelled},
    StatusCompleted:           {}, // 终态
    StatusCancelled:           {}, // 终态
}

func CanTransit(from, to OrderStatus) error {
    for _, t := range validTransitions[from] {
        if t == to { return nil }
    }
    return errs.New(errs.CodeInvalidState, "cannot transit from %s to %s", from, to)
}
```

**使用方式（service 层）**：

```go
func (s *Service) ConfirmAccept(ctx context.Context, orderID int64, escortID int64) (*OrderDTO, error) {
    o, err := s.repo.GetByID(ctx, orderID)
    if err != nil { return nil, err }

    if err := state.CanTransit(o.Status, state.StatusEscortConfirmed); err != nil {
        return nil, err  // 400 InvalidState
    }
    if o.EscortID != nil && *o.EscortID != escortID {
        return nil, errs.New(errs.CodeForbidden, "escort mismatch")
    }

    now := time.Now()
    o.Status = state.StatusEscortConfirmed
    o.Version++  // 乐观锁
    o.ConfirmedAt = &now

    if err := s.repo.UpdateWithVersion(ctx, o); err != nil {
        return nil, err
    }

    // commit 后发布事件(详见 §5.4 进阶)
    s.publisher.PublishOrderConfirmed(ctx, o)
    return ToDTO(o), nil
}
```

#### 5.1.2 转换合法性矩阵

| from \ to | selecting | pending_accept | confirmed | in_service | completed | cancelled |
|---|---|---|---|---|---|---|
| **selecting_escort** | ✓ | ✓ patient select | ✗ | ✗ | ✗ | ✓ |
| **escort_pending_acceptance** | ✓ 超时回退 | ✗ | ✓ accept | ✗ | ✗ | ✓ |
| **escort_confirmed** | ✗ | ✗ | ✓ | ✓ service_start | ✗ | ✓ |
| **in_service** | ✗ | ✗ | ✗ | ✓ | ✓ complete | ✓ |
| **completed** | ✗ | ✗ | ✗ | ✗ | ✓ | ✗ |
| **cancelled** | ✗ | ✗ | ✗ | ✗ | ✗ | ✓ |

> 实现见 `services/order/internal/state/order_state.go` 的 `validTransitions map[OrderStatus][]OrderStatus`。

#### 5.1.3 关键不变式

1. **乐观锁**：每次 `UPDATE orders SET status=$2, version=version+1 WHERE id=$1 AND version=$3`。冲突返回 `ErrConflict`。
2. **事件时序保证**：`commit DB tx → 然后 publish Kafka`。如果 publish 失败，事件会丢失但状态正确；对账任务需要扫 `order_events` 表对比 Kafka offset（v1.1 实现的 outbox pattern）。
3. **取消的去向**：取消时不直接改 status；要先校验 refund policy（参考 §5.3）+ 钱包是否已结算（参考 §5.2）。
4. **超时的归属**：`escort_pending_acceptance` 30s 超时由 **scheduler/scanner** 后台循环处理，移到 `selecting_escort`，**不**抛错。

### 5.2 钱包 T+7 结算

#### 5.2.1 资金流

```
订单 completed (T+0)
   │
   │  → order-service 发布 OrderCompletedEvent
   ▼
wallet-service 消费事件
   │
   │  → 写 pending_transactions 表（冻结金额，不进可用余额）
   │  → status = 'pending_settle'
   │
   │  → 7 天后（>= T+7）
   ▼
settle scanner 后台循环（每分钟扫）
   │
   │  → 满足条件的 pending_transactions
   │  → 移到 transactions 表（status='available'）
   │  → user.balance += amount（可用余额）
   ▼
用户在 wallet 看到可用余额
   │
   │  → 用户发起提现 → 走 admin 审批 → 出纳打款
```

#### 5.2.2 关键设计理由

- **T+7 而非 T+0**：防止洗钱 / 套现 / 退款穿仓。7 天覆盖大多数退款窗口。
- **金额分单位存储**：所有金额用 `int64` 表示"分"，**绝不**用 `float`。前端展示时 `cents / 100`。
- **多状态机钱包流水**：`pending_settle` → `available` → `withdrawing` → `paid` / `rejected`，每步独立事件，支持审计。

#### 5.2.3 退款对冲

```
订单 cancelled (any time)
   │
   │  ① 如果 wallet_transaction.status == 'pending_settle'
   │     → 直接 mark 'cancelled'，无任何资金动作
   │
   │  ② 如果 wallet_transaction.status == 'available'
   │     → 进入退款分段审核（§5.3）
   │     → 审批通过后 transactions.status='refunded'
   │
   │  ③ 如果 wallet_transaction.status == 'withdrawing' 或 'paid'
   │     → 必须走客服人工干预（管理员标记异常，走线下）
```

### 5.3 退款分段审核

```
用户发起退款申请
   │
   ▼
┌──────────────────┐
│   pending        │ ← 用户提交，订单管理员看到
└──────────────────┘
   │
   │  部门审批（无需金额阈值）
   ▼
┌──────────────────┐
│   dept_approved  │ ← 订单管理员通过
└──────────────────┘
   │
   │  财务审批（金额阈值触发）
   │  - 阈值以内：自动通过
   │  - 阈值以上：财务手动审批
   ▼
┌──────────────────┐
│  fin_approved    │
└──────────────────┘
   │
   │  出纳打款
   │  - 调用支付 service 真实退款
   │  - 标 wallet_transaction 'refunded'
   ▼
┌──────────────────┐
│   paid           │ ← 终态
└──────────────────┘

任一步可驳回：
   │  rejected → 用户可见退款失败原因
```

> 阈值在 `config/refund.yaml` 里，默认 `amount > 500_00` (500元) 触发财务审批。

### 5.4 publish-after-commit 模式

```
Service.UpdateStatus(ctx, order)
   │
   │  tx, _ := s.db.Begin(ctx)
   │  defer tx.Rollback()
   │
   │  err := s.repo.UpdateWithVersion(ctx, tx, order)  // 写库
   │  if err != nil { return err }
   │
   │  err = s.repo.InsertEvent(ctx, tx, OrderEscortSelectedEvent)  // 写 outbox
   │  if err != nil { return err }
   │
   │  tx.Commit()   ←── 在这里之后才能 publish
   │
   │  // 后台 goroutine 或者同步调，失败重试
   │  s.publisher.Publish(OrderEscortSelectedEvent)
   │  // 或者：s.outbox.PublishPending(ctx)  ←── 周期性兜底
   │
   │  return nil
```

**outbox pattern 解释**：
- 事件不直接 publish 到 Kafka；而是和业务数据**同事务**写入 `order_events` 表
- 后台 publisher 扫描 `order_events.status='pending'`，推送 Kafka，标 `published=true`
- 这样保证 **要么都成功，要么都失败**（at-least-once）

### 5.6 陪诊师 30s 锁定的工程细节

```go
// service 层
func (s *Service) SelectEscort(ctx, orderID, escortID) error {
    order, err := s.repo.GetByID(ctx, orderID)
    if err != nil { return err }
    if order.PatientID != currentUserID(ctx) { return ErrForbidden }

    // 1. Redis SETNX 30s 锁
    lockKey := fmt.Sprintf("orders:confirm:%d", orderID)
    acquired, err := s.lock.TryLock(ctx, lockKey, 30*time.Second)
    if !acquired {
        return ErrAlreadyInProgress  // 已有选人在飞
    }
    defer s.lock.Unlock(ctx, lockKey)  // defer 释放

    // 2. 校验候选有效性（match service 已确认该 escort 符合 hospital/city/package）
    if !s.match.IsEligible(ctx, escortID, orderID) {
        return ErrInvalidCandidate
    }

    // 3. 更新 DB + 写事件
    order.Status = state.StatusEscortPendingAccept
    order.SelectedEscortID = &escortID
    order.EscortPendingExpireAt = ptr(time.Now().Add(30 * time.Second))
    if err := s.repo.UpdateWithVersion(ctx, order); err != nil { return err }

    // 4. publish
    s.publisher.PublishOrderEscortSelected(ctx, order)
    return nil
}
```

```
scheduler 30s 超时处理（scheduler/timeout_scanner.go）：

   for scanner.tick(5s):
     rows := SELECT id, escort_pending_expire_at FROM orders
            WHERE status='escort_pending_acceptance'
              AND escort_pending_expire_at < NOW()
     for each row:
       order.Status = 'selecting_escort'
       order.SelectedEscortID = null
       repo.UpdateWithVersion(order)
       publisher.PublishOrderEscortTimeout(order)
       // 解 Redis 锁让患者能重新选
       lock.Unlock(orders:confirm:{id})
```

## §6 设计原则与惯用法

### 6.1 防御式编程

#### 6.1.1 后端

- **绝不信任前端**：handler 必须再次校验所有入参，不允许"前端验过了就行"
- **nil 防御**：结构体字段 nil 检查统一用 `if x != nil { ... }`；指针解引用前必检
- **错误 wrap**：`return fmt.Errorf("order.Create: %w", err)`，根因保留
- **defer 释放**：锁 / tx / close 全部 defer，即使 panic 也走得到
- **超时显式**：所有 ctx 带 5-30s 超时，绝不 `context.Background()`
- **ratelimit**：敏感写接口（下单、提现、改密码）必须 ratelimit，配置文件决定阈值

#### 6.1.2 前端

- **API 调用必带 onError**：每个 `await api.xxx()` 必须 `.catch()` 或外层 try/catch
- **UI 兜底**：`UiEmpty` / `loading` / `error 重试按钮` 三态必有
- **testid 必有**：组件内部渲染的元素必须带 `data-testid="..."`，便于 e2e 和单测
- **不假设 uni 全局存在**：`if (typeof uni !== 'undefined') { ... }`

### 6.2 接口契约化（API Contract First）

#### 6.2.1 后端

- 任何出现在 2+ 服务的 DTO / 事件名 / 错误码进 `shared/contracts/`
- 接口定义前写 spec（specs/），再写测试，再写实现（TDD）
- 改动现有 contract 视为 breaking change，需 CHANGELOG + 主要负责人 review

#### 6.2.2 前端

- 每个 `api/<svc>.ts` 配 `api/<svc>.spec.ts`，断言：
  - URL 路径正确
  - method 正确
  - 入参序列化方式（JSON / querystring）
  - 返回类型 interface 与 spec 一致

### 6.3 关注点分离

| 维度 | 该在哪 | 不该在哪 |
|---|---|---|
| HTTP 解析 | handler | service |
| 业务规则 | service | handler / repo |
| SQL | repo | service / handler |
| 状态机合法性 | state | service（服务调用，自身不 IO） |
| 事件发布 | service（commit 后） | handler |
| 角色检查 | middleware 或 handler 入口 | service |
| 金额单位转换（cents→元） | 前端 UI 层 | 后端 storage |

### 6.4 测试金字塔

```
        ╱╲
       ╱  ╲         e2e（慢，少量，跨域）
      ╱    ╲
     ╱──────╲       集成（repo + 真 PG）
    ╱        ╲
   ╱──────────╲     单元（快，大量）
  ╱────────────╲
```

- **单元**：纯函数、状态机、错误码、SQL builder
- **集成**：repo 用 testcontainers；service 用 mock repo + 真 redis
- **handler**：httptest 跑完整链；service mock
- **e2e**：docker-compose 起全栈 + Playwright 跑核心流
- **覆盖率红线**：核心 100%（state/contracts/order service），其余 ≥70%

### 6.4.2 v2.1 引入的"快照 vs 实现细节"取舍

v1.1 之前的测试偏向"全树快照"(snapshot file diff),CI 上偶发因渲染细节变化而失败。v2.1 起改用**精确断言** + **DOM 结构断言**(详见 §3.7.1)。

| 维度 | 全树快照 | DOM 结构断言(推荐) |
|---|---|---|
| 失败信号 | 整张 snapshot | 单个 testid 缺失 |
| 维护成本 | 高(细节变化频繁) | 低(testid 稳定) |
| 反馈速度 | 慢(diff 大) | 快(单断言) |
| 误报率 | 高 | 低 |

**约定**:
- ✅ 列表渲染、关键按钮、snapshot 卡 → testid 断言
- ✅ 表单输入、状态变化 → vm ref / wrapper.emitted 断言
- ❌ 禁止用 `toMatchSnapshot()` 测关键路径
- ❌ 禁止依赖多次 `await flushPromises()` 的执行顺序

**例外**:`web-design.md` / `web-user-manual.md` 的纯 UI 文案,允许整树快照作为"非功能回归"。

### 6.5 渐进式升级（v1 → v2）

v2 unified-app 把 v1 三端（patient-miniapp + escort-app + admin-web）**合并**为 1 个 uni-app 工程。

```
v1 三端 → v2 unified-app
───────────────────────────────────
patient-miniapp (Flutter + uni-app x)
  + escort-app (Flutter + Riverpod)
  + admin-web (React 18 + AntD)
              ↓ 合并
        unified-app (uni-app 3)
            ├── patient 域
            ├── escort  域
            └── admin   域
───────────────────────────────────
架构共同点：
  - 共享 types/ （受 API contract 约束）
  - 共享 api/<svc>.ts
  - 共享 store/auth.ts （多角色）

  1. 先迁 patient 域（量大但简单，验证流程）
```

### 6.7 错误处理统一约定

#### 6.7.1 后端

```go
// 业务错误：用 errs 包
if order == nil {
    return nil, errs.New(errs.CodeNotFound, "order %d", id)
}

// wrap 底层错误
if _, err := db.Exec(...); err != nil {
    return nil, fmt.Errorf("insert order: %w", err)
}

// 上层 handler 翻译成 HTTP
func respondError(c *gin.Context, err error) {
    if e, ok := err.(*errs.Error); ok {
        c.JSON(e.HTTPStatus(), gin.H{"code": e.Code, "message": e.Message})
        return
    }
    c.JSON(500, gin.H{"code": "internal", "message": "网络繁忙"})
}
```
