# 02 · 角色与权限

## 2.1 角色总览

平台采用三类角色的清晰划分，所有权限严格按角色收敛，避免出现"既是运动员又是裁判员"的情况。

| 角色 | 终端 | 入口 | 关键身份标识 |
| :-- | :-- | :-- | :-- |
| **患者**（Patient） | iOS / Android / 小程序 | 患者端 | `role = patient`，需实名 |
| **陪诊师**（Escort） | iOS / Android / 小程序 | 陪诊师端 | `role = escort`，需实名 + 资质审核通过 + 培训考核通过 |
| **管理员**（Admin） | Web 后台 | PC 浏览器 | `role = admin`，**仅 Web 端登录** |

> 📌 **一个手机号原则上只允许一种角色**。  
> 若用户既想下单又想接单，需注册两个账号（监管 / 合规 / 利益冲突考虑）。  
> 后续可支持"切换身份"模式，但需明确提示并在审计日志留痕。

## 2.3 账号体系

```
用户账号（user）
├── 唯一手机号
├── 微信 openid（可选绑定）
├── 实名信息（姓名 + 身份证 + 人脸）
├── 角色：patient | escort | admin
└── 状态：active | frozen | canceled
```

- **手机号**：唯一索引；改手机号需短信验证码 + 老手机号二次确认。
- **微信 openid**：仅用于快捷登录和分享，不作为唯一身份。
- **实名**：调用第三方实名服务（公安二要素 + 活体），返回"通过/不通过"，平台不存储明文身份证号。
- **登录态**：JWT + refresh token，移动端持久化到 Keychain / Keystore。

## 2.4 角色切换 / 多角色策略

### 2.4.1 单手机号单角色（默认）

- 注册时选定角色；不允许同手机号注册其他角色。
- 防止陪诊师"自买自评"、患者与陪诊师利益冲突。

### 2.4.2 内部员工特殊处理

- 平台内部员工统一走企业邮箱 + 单独域管理后台（`admin.<domain>`）；
- 内部员工**不得**在患者端或陪诊师端持有账号（需独立测试账号）。

## 2.5 权限细化规则

### 2.5.1 患者

| 行为 | 前置条件 |
| :-- | :-- |
| 浏览 / 加购物车 | 无 |
| 创建订单 | 已登录 + 已实名 |
| 支付订单 | 已绑定微信支付 |
| 评价 | 订单状态 = "已完成" 且 在 14 天评价期内 |
| 申请发票 | 订单已支付且未全额退款 |
| 注销账号 | 无进行中订单；钱包余额 ≤ 0 或已提现 |

### 2.5.2 陪诊师

| 行为 | 前置条件 |
| :-- | :-- |
| 注册 | 无 |
| 进入抢单池 | 已实名 + 资质审核通过 + 培训考核通过 + 协议已签 |
| 接单 | 状态 = 在线、空闲时段、无未处理申诉 |
| 申请提现 | 已绑定本人银行卡 / 微信钱包；累计可提现金额 ≥ 100 元 |
| 注销 | 无进行中订单；钱包余额已清零 |

### 2.5.3 管理员

| 行为 | 前置条件 |
| :-- | :-- |
| 登录后台 | 内网 + 双因素认证（密码 + 一次性码） |
| 操作资金 | 财务权限 + 二次确认 |
| 修改配置 | 运营权限 + 变更日志 |
| 删除数据 | 超管权限 + 多人复核 |

---

## 2.6 数据权限（防越权）

- **患者只能看自己的订单、评价、钱包**；任何"看别人数据"的接口都需 RBAC + 资源归属校验。
- **陪诊师只能看分配给自己的订单**和**自己的钱包 / 评价**。
- **管理员按部门 / 城市**划分数据范围，城市经理只看本市订单。
- 所有查询接口必须在网关层校验资源归属，**不允许"传 ID 就返回"**。

---

## 2.7 审计与日志

- 所有写操作（创建订单、改派、退款、提现、修改配置等）必须写**审计日志**，包含操作人、操作时间、变更前后值、IP、UA。
- 审计日志**不可被业务账号删除**；至少保留 5 年（满足合规要求）。
- 涉及资金的变更必须二次校验，并触发风控规则。
